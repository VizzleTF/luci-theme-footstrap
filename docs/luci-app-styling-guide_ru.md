# Как стилизовать приложение LuCI, чтобы оно работало под любой темой

Правила для авторов пакетов `luci-app-*`. Они действуют для любой темы LuCI; поведение, которое
есть только у footstrap, помечено отдельно.

*English version: [luci-app-styling-guide.md](luci-app-styling-guide.md).*

Каждое правило взято из реального бага в популярном приложении. Каждый баг виден только на теме,
которую автор не проверял. Что эти приложения делают с общей страницей, собрано в
[third-party-apps.md](third-party-apps.md).

ОБЯЗАТЕЛЬНО и ЗАПРЕЩЕНО отмечают правило, без которого страницы ломаются. РЕКОМЕНДУЕТСЯ и
НЕ РЕКОМЕНДУЕТСЯ отмечают сильный совет; для исключения нужна причина.

В этом гайде три термина значат вот что:

| Термин | Что значит |
|---|---|
| представление | модуль `view` в LuCI, который рисует страницу приложения |
| таблица стилей | содержимое одного `<style>` или файла из `<link>` |
| фолбэк | запасное значение во втором аргументе `var()`: `var(--text-color-high, #333)` |

## Коротко

Если не читаете ничего другого, следуйте этим семи правилам:

1. Возвращайте свой `<style>` внутри дерева представления. Никогда не добавляйте его в `<head>`.
2. Начинайте каждый класс, id и кастомное свойство с имени приложения.
3. Берите каждый цвет из 26 экспортных имён (`--*-color-*` и `--on-*-color`). Это 7 семейств из
   [таблицы](#экспортный-ярус-26-имён); у каждого имени ставьте фолбэк-литерал.
4. Для текста на цветной заливке берите `--on-*-color` того же семейства.
5. Узнавайте тёмный режим у темы. Никогда не используйте `prefers-color-scheme`.
6. Подстраивайте раскладку под свой контейнер. Никогда под вьюпорт.
7. Делайте работу в `render()`. Никогда в `window.onload`.

[Чек-лист](#чек-лист) в конце покрывает каждое правило.

## S. Где живёт ваш CSS

Представление LuCI рисуется в браузере и подменяется внутри `#view`. Новая тема может быть SPA: между
кликами она не перезагружает страницу. Поэтому место вашего `<style>` решает, сколько он живёт и
какие страницы задевает.

### S-1. `<style>` ОБЯЗАТЕЛЬНО лежит в дереве, которое возвращает представление

Зачем: тогда он умирает вместе с представлением, как остальная ваша разметка.

```js
// Плохо: остаётся в <head> на всю сессию
document.head.appendChild(E('style', [ css ]));

// Хорошо: живёт ровно столько, сколько представление
return E([], [
    E('style', [ css ]),
    E('div', { 'class': 'myapp-root' }, …)
]);
```

Штатный LuCI так делает в `package-manager.js`, `nftables.js` и `aria2/log.js`.

Представление на `form.Map` возвращает `m.render()`: промис с узлом карты. Положите `<style>`
внутрь этого узла, как делает `luci-app-smartdns`:

```js
return m.render().then(node => {
    node.classList.add('myapp-root');   // корень для ваших имён и container-запросов
    node.prepend(E('style', [ css ]));
    return node;
});
```

Что ломается иначе: таблица стилей в `<head>` безобидна при полной загрузке страницы, потому что следующий
клик её выбрасывает. Под SPA-темой она остаётся и перестилизует каждую страницу, которую пользователь
откроет дальше.

- `luci-app-filemanager` так прячет штатные кнопки Save, Apply и Reset
  (`.cbi-button-save { display: none !important }`). Каждая config-страница за сессию их теряет.
- `luci-app-banip` и `luci-app-adblock` делают то же через `<link>`.

### S-2. НЕ РЕКОМЕНДУЕТСЯ вставлять CSS при загрузке модуля

Зачем: `<style>`, добавленный на верхнем уровне модуля, создаётся один раз на страницу. Модуль
закэширован, поэтому эта таблица стилей больше не будет создана. Тема, которая её убрала, не
сможет её вернуть, и ваш виджет теряет стили.

То же происходит с библиотекой, которая сама вставляет свой CSS. Так делает ACE со своим
14-килобайтным `ace_editor.css`.

S-2 — крайняя мера; где можно, используйте S-1. Если вставлять так всё же приходится, сделайте
вставку идемпотентной: повторный вызов не добавляет вторую копию. Рассчитывайте, что таблица стилей
останется на всю жизнь страницы.

### Что footstrap делает с таблицей стилей в `<head>`

Действовать нужно только по S-1. Этот блок лишь объясняет, какие таблицы стилей в `<head>`
footstrap терпит.

footstrap никогда не удаляет таблицу стилей. Он оставляет SPA-навигацию включённой, пока таблица
стилей может покрасить только вашу страницу. Таблица стилей безопасна, если каждый её селектор подходит под один из пунктов:

- Селектор называет только ваши классы: `.ace_*`, `.hexview`, `.myapp-card`.
- Селектор называет штатный виджет, привязанный к вашему собственному имени:
  `#cbi-myapp-section > .cbi-section-remove`, `.myapp-table th.sortable.active`.
  Без вашей секции или таблицы они ничего не находят.
- Это голый селектор, который объявляет только ваши кастомные свойства:
  `:root { --myapp-accent: … }`.

Безопасными не считаются:

- Аргумент `:not()` не привязывает селектор к вашей странице.
  `.cbi-button-save:not(.my-save-button)` по-прежнему находит каждую штатную кнопку Save на каждой
  странице.
- `:root { color-scheme: light dark }` объявляет больше, чем кастомное свойство.

Любая другая таблица стилей переводит следующую навигацию в полную загрузку страницы. Приложение продолжает
работать; пользователь ждёт одну обычную загрузку. Настоящие примеры из 30 приложений с наибольшим
числом звёзд: `.cbi-button-save { display: none }`, `.error { … }`, `h4 { … }`,
`div > label + select { … }`, `svg text { … }`.

## N. Имена

Вы делите страницу с темой и со всеми остальными приложениями.

### N-1. Классы и id ОБЯЗАТЕЛЬНО начинаются с имени вашего пакета

Зачем: словарные слова сталкиваются с темой и с другими приложениями.

```css
/* Плохо */  .hidden { … }   .label { … }   .toast { … }
/* Хорошо */ .myapp-hidden { … }   #cbi-myapp-status { … }
```

Имена, которые уже конфликтуют в реальных приложениях: `.hidden`, `.label`, `.description`, `.centered`,
`.skeleton`, `.toast`, `.dialog-title`, `.flex-row`, `.log-line`, а также
`[hidden] { display: none !important }` у `luci-lib-taskd`.

### N-2. Кастомные свойства РЕКОМЕНДУЕТСЯ объявлять на своём корневом элементе, а не на `:root`

Зачем: `:root` общий для всех. Токен темы с тем же именем перекрашивается без предупреждения. Если
вы всё же используете `:root`, каждое имя там ОБЯЗАТЕЛЬНО несёт ваш префикс: `--myapp-*`.

```css
/* Плохо: hex-редактор luci-app-filemanager */
:root { --clr-background: …; --clr-border: …; --clr-highlight: …; }

/* Хорошо: так OpenClash ограничивает свои ~90 свойств классом .oc */
.oc { --oc-accent: …; }
```

Файл-менеджер также пишет `color-scheme` на `:root`, а это меняет всю страницу.

### N-3. ЗАПРЕЩЕНО везти глобальный ресет или CSS-фреймворк

Зачем: они перестилизуют собственные сайдбар, шапку и меню темы.

```css
/* Плохо: OpenClash, дважды */
* { margin: 0; padding: 0 }
/* Плохо: vssr */
@import url(pure.css);
```

### N-4. ЗАПРЕЩЕНО перестилизовать штатные селекторы LuCI за пределами своей страницы

Зачем: `.cbi-button-up`, `.cbi-value`, `.cbi-section-table-titles`, `ul.dropdown`, `table th` и
`pre` принадлежат теме. Ваш CSS вне слоёв, поэтому бьёт любой каскадный слой темы. footstrap ловит
такую таблицу стилей и переносит её в свой слой `theme`. Другие темы этого не делают.

В свой слой footstrap переносит только таблицы стилей, которые перестилизуют штатные селекторы.
Таблица стилей только с вашими собственными именами остаётся вне слоёв и побеждает тему.

```css
/* Плохо: каждая таблица на каждой странице */
table th { … }
/* Хорошо: только внутри вашей страницы */
.myapp-root table th { … }
```

Внутри вашей страницы то же правило работает на вас. Там ваш CSS, привязанный к вашим именам, бьёт тему без
`!important`. См. [C-4](#c-4-не-рекомендуется-использовать-important-чтобы-победить-тему).

## C. Цвет

### C-1. Цвета ОБЯЗАТЕЛЬНО берутся из экспортного яруса, с литеральным фолбэком

Зачем: каждая тема LuCI задаёт одни и те же 26 имён. Литерал верен только на той палитре, на
которую вы смотрели.

```css
/* Плохо */
color: #333;
background: white;

/* Хорошо */
color:            var(--text-color-high, #333);
background-color: var(--background-color-low, #f5f5f5);
border-color:     var(--border-color-medium, #ddd);
color:            var(--error-color-medium, #f44336);
```

Полный список приведён ниже, в разделе [Экспортный ярус](#экспортный-ярус-26-имён).

Цвет без своего семейства всё равно берётся из 26 имён:

| Нужно | Берите |
|---|---|
| нейтральный или серый бейдж | `--background-color-medium` и `--text-color-medium` |
| цвет «информация» | семейство `primary` |

У footstrap больше осей, чем светлый и тёмный режим. Эти оси тянут экспортный ярус за собой:

- `:root[data-palette]` подменяет весь набор цветов: default, hicontrast, bootstrap, 2020, forum.
- Слайдер Tint сдвигает оттенок каждой поверхности (`:root[data-tint]` с `--fs-tint-h`, любой
  оттенок 1–360).

Карточка `#f7f7f7`, подобранная под дефолтную панель, неверна, как только пользователь выбрал
hicontrast. Вручную подобранный янтарный неверен, как только он сдвинул слайдер Tint на 40°.

### C-2. Текст на цветной заливке ОБЯЗАТЕЛЬНО использует парный `--on-*-color`

Зачем: каждый `--on-*-color` проходит WCAG AA поверх уровня `-high` своего семейства. Правильный
цвет текста свой для каждой палитры и режима, поэтому жёстко заданный `#fff` на части из них
проваливается.

Заливайте уровнем `-high`. Уровни `-medium` и `-low` — цвета текста, контраст текста на них не
гарантирован.

```css
/* Плохо */
.myapp-badge { background: var(--success-color-high, #2e7d32); color: #fff; }
/* Хорошо */
.myapp-badge { background: var(--success-color-high, #2e7d32); color: var(--on-success-color, #fff); }
```

### C-3. ЗАПРЕЩЕНО читать имена `--fs-*`

Зачем: это приватный ярус footstrap. footstrap переименовывает их, когда ему нужно, и ни у одной
другой темы их нет.

В `cascade.css` больше сотни свойств `--fs-*`: `--fs-accent`, `--fs-panel2`, `--fs-radius`,
`--fs-dim`, шкала z-index. Их имена короче и понятнее экспортных. Контракт — только 26 имён
`--*-color-*`.

Это справка, действий от вас не требуется. Таблица стилей приложения стоит вне слоёв и бьёт любой слой темы. Одно приложение,
написавшее `:root { --accent: … }` или `:root { --text-color-high: … }`, перекрасило бы тему.
Поэтому footstrap читает только свои имена `--fs-*` и выводит из них экспортные
(`styles/02-tokens.css`).

### C-4. НЕ РЕКОМЕНДУЕТСЯ использовать `!important`, чтобы победить тему

Зачем: ваш CSS, привязанный к вашим именам, стоит вне слоёв. Такой CSS и так бьёт любой слой
темы, а ваш `:root` не может перекрасить тему (см. [C-3](#c-3-запрещено-читать-имена---fs-)).

Если в вашем приложении есть `!important`, чтобы победить тему, удалите его. Побеждал не он.

### C-5. ЗАПРЕЩЕНО задавать поверхность литеральным цветом

Зачем: литеральная поверхность выглядит неправильно в другом режиме.

- passwall: `background: white` на модалке с `position: fixed`. На тёмной странице это белая коробка.
- justclash: `#1e1e1e` на терминале логов. На светлой странице это чёрная коробка.

Для приподнятой поверхности, например модалки или карточки, берите `--background-color-high`.

### C-6. ЗАПРЕЩЕНО класть текст цвета C на полупрозрачную подложку того же цвета C

Зачем: полупрозрачная подложка тянет фон к цвету текста и съедает контраст. Результат зависит от того, что под ним,
поэтому безопасной прозрачности не существует.

```css
/* Плохо */
.myapp-chip { color: var(--error-color-medium, #f44336); background: rgb(244 67 54 / 15%); }
/* Хорошо: непрозрачная поверхность, цвет несёт рамка */
.myapp-chip { color: var(--error-color-medium, #f44336);
              background: var(--background-color-high, #fff);
              border: 1px solid var(--error-color-medium, #f44336); }
```

### C-7. ЗАПРЕЩЕНО использовать `<font color>`

Зачем: `<font color="green">` (dockerman, ssr-plus, OpenClash) исчезает на половине палитр.
Используйте `--success-color-medium`.

## Экспортный ярус: 26 имён

Эта таблица и есть весь контракт. Ничего другого в контракт не входит. Все 26 имён — цвета.

| Семейство | Имена | Замечания |
|---|---|---|
| Поверхности | `--background-color-high` / `-medium` / `-low` | высота: `high` — приподнятое (карточка), `low` — утопленное (страница) |
| Линии | `--border-color-high` / `-medium` / `-low` | `high` — видимая линия, `low` — волосяная |
| Текст | `--text-color-highest` / `-high` / `-medium` / `-low` | четыре уровня |
| Акцент | `--primary-color-high` / `-medium` / `-low`, `--on-primary-color` | |
| Успех | `--success-color-high` / `-medium` / `-low`, `--on-success-color` | |
| Предупреждение | `--warn-color-high` / `-medium` / `-low`, `--on-warn-color` | семейство называется `warn` |
| Ошибка | `--error-color-high` / `-medium` / `-low`, `--on-error-color` | |

### Имена, которых не существует

Ни одна тема LuCI не определяет эти имена, поэтому всегда срабатывает ваш фолбэк-литерал:

| Вы написали | Берите вместо него |
|---|---|
| `--warning-color-*` | `--warn-color-*` |
| `--text-color` | `--text-color-high` |
| `--secondary-color-*` | замены нет; выберите семейство выше |
| `--font-sans`, `--font-mono`, `--disabled-opacity` | замены нет; ярус только про цвет |

Два реальных случая:

- podkop пишет `var(--warn-color-medium, orange)` 7 раз. Это правильно: так красится янтарный цвет
  темы. Переименование в `--warning-color-medium` уронило бы все 7 в фолбэк `orange`.
- justclash пишет `--text-color` 6 раз. Такого имени нет; правильное — `--text-color-high`.

### Что гарантирует ярус

footstrap замерил 70 сочетаний: {светлый, тёмный} × {default, hicontrast, bootstrap, 2020, forum}
× семь положений слайдера Tint. В каждом из них:

- Каждый уровень `text`, `primary`, `success`, `warn` и `error` проходит WCAG AA как текст на всех
  трёх поверхностях `--background-color-*`. Ставьте любой из них в `color:` без проверки.
- Каждый `--on-*-color` проходит AA поверх своего цвета, использованного заливкой.
- `high`, `medium` и `low` — три разных цвета. «Нет данных» в `--primary-color-low` читается тише
  живого значения в `-high`.

Две оговорки:

- У `--background-color-*` `high` значит «приподнятое», а не «сильнее». У всех остальных семейств
  `high` — самый сильный цвет.
- `-low` — самый бледный уровень, который палитра может себе позволить. Текст в нём читается,
  но бледнее уровня нет.

## D. Тёмный режим

### D-1. ЗАПРЕЩЕНО определять тёмный режим через `prefers-color-scheme`

Зачем: `prefers-color-scheme` сообщает об операционной системе, а не о теме. У каждой новой темы
LuCI есть свой переключатель светлого и тёмного режима. Пользователь, включивший тёмный режим на
светлой ОС, получит вашу светлую карточку на тёмной странице. Этот баг есть у netspeedtest, vssr,
passwall и штатного `ustreamer`.

### D-2. НЕ РЕКОМЕНДУЕТСЯ определять тёмный режим вообще

Зачем: если каждый цвет взят из экспортного яруса, тёмный режим уже работает. `luci-app-nikki` не
читает состояние темы и выглядит правильно на любой теме.

### D-3. Если без определения не обойтись, ОБЯЗАТЕЛЬНО спрашивайте тему

Проверяйте в таком порядке:

```js
function isDark() {
    const root = document.documentElement;
    if (root.dataset.darkmode) return root.dataset.darkmode === 'true';  // OpenClash, luci-app-internet-detector
    if (root.dataset.theme)    return root.dataset.theme === 'dark';     // footstrap, justclash
    if (root.dataset.bsTheme)  return root.dataset.bsTheme === 'dark';   // Bootstrap 5
    const m = getComputedStyle(document.body).backgroundColor.match(/\d+/g);   // любая тема
    return m && m.length >= 3
        ? (0.299 * +m[0] + 0.587 * +m[1] + 0.114 * +m[2]) / 255 < 0.5
        : false;
}
```

```css
/* Плохо */
@media (prefers-color-scheme: dark) { .myapp-card { … } }
/* Хорошо: сам следует за темой */
.myapp-card { background: var(--background-color-low, #fff); }
/* Хорошо, только если нужно переопределение лишь для тёмного режима */
:root[data-theme="dark"] .myapp-card { … }
```

Факты, на которых стоит этот код:

- Приложения используют четыре диалекта. footstrap ставит три из них на `:root` до первой
  отрисовки: `data-darkmode`, `data-theme` и `data-bs-theme`.
- `luci-app-internet-detector` вешает свои тёмные стили на `:root[data-darkmode="true"]`, поэтому
  на footstrap выглядит правильно без единой правки.
- Последняя проверка, по яркости фона, работает только потому, что темы держат фон `body` непрозрачным. Не
  полагайтесь на то, что какой-то один атрибут существует.

## W. Редакторы и тяжёлые виджеты

### W-1. Цветовая тема редактора ОБЯЗАТЕЛЬНО следует за режимом страницы

Зачем: жёстко заданная тёмная тема даёт чёрный редактор на светлой странице. mosdns и AdGuardHome
жёстко задают CodeMirror тему `dracula`; ssclash задаёт ACE тему `tomorrow_night_bright`.

Выбирайте тему редактора по `isDark()` из
[D-3](#d-3-если-без-определения-не-обойтись-обязательно-спрашивайте-тему). OpenClash делает это
правильно: `themeExtension(isDark)`.

### W-2. Вложенная библиотека ОБЯЗАТЕЛЬНО лежит под вашим собственным путём

Зачем: два приложения, которые везут разные версии в общий путь, перезаписывают друг друга.
AdGuardHome везёт CodeMirror в `/luci-static/resources/codemirror/`.

Кладите её под `/luci-static/resources/view/<YOURAPP>/`.

### W-3. Iframe РЕКОМЕНДУЕТСЯ делать по образцу штатного `luci-app-ttyd`

Делайте так:

- Задайте размер `width: 100%; min-height: …; resize: vertical`.
- Берите порт из UCI.
- Используйте тот же протокол, что у страницы.

Не делайте так:

- Не задавайте порт жёстко. dockerman использует `:7682`.
- Не красьте iframe в `background: #fff`, как netspeedtest. Встроенная страница выбирает свои
  цвета сама.

### W-4. `z-index` РЕКОМЕНДУЕТСЯ держать в обычном диапазоне

Зачем: собственные оверлеи и выпадающие меню темы не могут встать выше огромного значения.
Дропдаун passwall использует `2147483647`; полноэкранный редактор OpenClash — `999999 !important`.
Ничему из того, что вы рисуете, не нужно быть выше всего.

### W-5. ЗАПРЕЩЕНО ставить `body { pointer-events: none }`

Зачем: если навигация случится, пока это свойство стоит, весь интерфейс перестаёт отвечать.
passwall ставит его, пока открыта его модалка.

## L. Раскладка

### L-1. Брейкпоинты РЕКОМЕНДУЕТСЯ привязывать к контейнеру, а не к вьюпорту

Зачем: тема ставит сайдбар рядом с вашей страницей. У footstrap он шириной 224 px. На экране
1024 px ваша колонка около 740 px, а `@media (max-width: 768px)` всё ещё говорит «десктоп».

Приложения, которые складывают карточки по вьюпорту, ломаются ровно в этой полосе: justclash на
56rem, podkop на 900 px, netspeedtest на 768 px.

```css
/* Плохо */
@media (max-width: 768px) { .myapp-cards { flex-direction: column; } }
/* Хорошо */
.myapp-root { container-type: inline-size; }
@container (max-width: 768px) { .myapp-cards { flex-direction: column; } }
```

Выбирайте брейкпоинт по ширине, которая нужна вашим карточкам, а не по размеру устройства.
`container-type` заставляет элемент игнорировать ширину своих детей, поэтому ставьте его на блок,
который заполняет свою колонку.

Если `@container` использовать нельзя, измерьте свой контейнер в JS и поставьте класс.

### L-2. В таблицах НЕ РЕКОМЕНДУЕТСЯ сочетать `table-layout: fixed` с `min-width` на каждой ячейке

Зачем: это мешает теме сворачивать строки таблицы в карточки на узком экране. Так делает
filemanager.

### L-3. Контейнерам НЕ РЕКОМЕНДУЕТСЯ задавать фиксированную ширину в px

```css
/* Плохо */  .myapp-panel { width: 900px; }
/* Хорошо */ .myapp-panel { width: 100%; max-width: 900px; }
```

## P. Время жизни страницы

Новая тема может создать ваше представление заново, не перезагружая страницу. На классической теме эти
правила ничего не стоят.

### P-1. ЗАПРЕЩЕНО делать работу в `window.onload` или `DOMContentLoaded`

Зачем: оба события срабатывают один раз на страницу. После первой навигации ваш обработчик больше
не запускается. Так ломаются diskman и `optimize_cbi_ui.htm` у passwall.

Делайте работу в `render()`.

### P-2. Периодические опросы и таймеры ОБЯЗАТЕЛЬНО останавливаются, когда представление уходит

Зачем: оставшийся `setInterval` продолжает работать на каждой странице после вашей.

Регистрируйте периодические опросы через `L.Poll`; LuCI остановит их за вас. Любой другой `setInterval`
очищайте сами.

### P-3. ЗАПРЕЩЕНО добавлять долгоживущие узлы в `document.body`

Зачем: они переживают подмену представления. Так делают контейнер тостов podkop и диалог taskd.

Кладите их в дерево представления.

### P-4. ЗАПРЕЩЕНО вешать обработчик `popstate`, который сам переходит на другую страницу

Зачем: он гоняется с роутером темы, и переход делают оба. Так делает istore.

### P-5. Прячьте штатные кнопки через представление, а не через CSS

Правило: если представление не должно показывать штатную кнопку, её обработчик ОБЯЗАТЕЛЬНО
ставится в `null`: `handleSave`, `handleSaveApply`, `handleReset`. Обработчик `null` убирает кнопку,
поэтому оставьте те, что нужны форме для сохранения.

Зачем: это штатный способ. Ему не нужен `!important`, и он не протекает на следующую страницу.
Так делают `luci-app-partexp` и `luci-app-ttyd`.

```js
// Плохо: прячет Save на каждой странице после вашей (см. S-1)
document.head.appendChild(E('style', [ '.cbi-button-save { display: none !important }' ]));

// Хорошо: файл представления начинается с 'require view';
return view.extend({
    handleSave: null,
    handleSaveApply: null,
    handleReset: null,
    render() { … }
});
```

## Чек-лист

Отметьте каждую строку перед публикацией:

- [ ] S-1: `<style>` лежит внутри дерева представления, а не добавлен в `<head>`.
- [ ] N-1, N-2: каждый класс, id и кастомное свойство начинается с имени приложения.
- [ ] N-2, N-3: кастомные свойства объявлены на вашем корневом элементе, а на `:root` — только `--myapp-*`; нет `* { … }`; нет
      CSS-фреймворка.
- [ ] N-4: нет штатных селекторов `.cbi-*`, `table` или `pre` вне вашего поддерева.
- [ ] C-1: каждый цвет — одно из 26 экспортных имён; литерал встречается только как его фолбэк;
      `warn`, а не `warning`.
- [ ] C-2: текст на цветной заливке использует `--on-*-color`, а не жёстко заданный `#fff`.
- [ ] C-3: `--fs-*` нигде не читается.
- [ ] C-4: нет `!important`, чтобы победить тему.
- [ ] D-1, D-2: тёмный режим не определяется вообще или берётся из `data-darkmode`, `data-theme`, `data-bs-theme` или яркости body,
      а не из `prefers-color-scheme`.
- [ ] W-1: тема редактора следует за режимом страницы.
- [ ] L-1: раскладка следует за контейнером, а не за вьюпортом.
- [ ] P-5: ненужная штатная кнопка убрана обработчиком `null`, а не спрятана через CSS.
- [ ] P-1, P-3, P-4, W-4: нет `window.onload`, нет остатков на `body`, нет обработчика `popstate`,
      нет `z-index: 2147483647`.
